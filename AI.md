## Выбор для проекта

Проект предусматривает HTTP-сервис на Go и синхронную фиксацию бюллетеня в PostgreSQL. В первоначальной схеме CDN отдавал страницу опроса. В текущей версии её отдаёт публичный Go API из памяти. Для промышленного контура ключ браузера в пределах опроса определяет шард. Запросы одного зрителя попадают к одному владельцу данных, а голоса за самый популярный вариант распределяются между шардами. Доказательство требуемой мощности потребует замеров на выбранном оборудовании с репликацией, повторами и профилем пика. Подробности и критерии проверки собраны в [проекте архитектуры](DESIGN.md).

## Какие предположения отбросили

- **Считать, что проголосует только часть зрителей.** В условии прямо сказано, что голосуют все зрители. Число просмотров также определяет объём раздачи страницы. Повторы увеличивают число запросов записи сверх числа зрителей.
- **Определять зрителя по IP.** За одним адресом мобильного оператора может находиться множество людей. Для базовой защиты точнее описать фактическую гарантию — один бюллетень на идентификатор браузера в конкретном опросе. Другой браузер или очистка его данных позволяют проголосовать повторно.
- **Использовать очередь и Redis с первого дня.** Очередь позволяет пережить паузу подсчёта во время эфира, но усложняет ответ на два вопроса — какой голос победил при повторе и когда итог можно объявить окончательным. К этой альтернативе имеет смысл вернуться, если синхронное хранилище на пике не укладывается в допустимую задержку или стоимость.
- **Рассчитать число узлов без измерения.** Для выбора размера кластера нужны испытания на нашей схеме данных с выбранным режимом подтверждения записи.

При рецензировании документа обнаружилась ещё одна тонкость. После перезапуска primary локальная запись может стать видимой раньше, чем успела попасть на синхронную реплику. В промышленной схеме это учтено при повторной отправке бюллетеня. Проверены расчёт пика, пересчёт байтов в биты, пример с числом шардов и взаимные ссылки между документами.

Результат этого этапа — архитектурный документ и журнал решений. Реализация, испытания на отказ и собственные замеры относятся к следующему этапу.

## Уточнение о числе участников

> не, ну если голосуют все, то давай всех считать

В проекте закреплён один контрольный эфир со 100 млн отдельных зрителей. При одном повторе у каждого десятого зрителя 110 млн плановых POST должны дать ровно 100 млн бюллетеней. В дизайн добавлена проверка по каждому токену и варианту. Для контрольного опроса A/B ожидаются 90 млн ответов A и 10 млн ответов B. Это критерии будущего испытания.

## Реализация приёма голоса

> давай теперь писать код по этой структуре. начнем с POST голоса, поднимем postgres и kafka в compose и проверим запись интеграционным тестом

ИИ реализовал HTTP-обработчик, проверку правил опроса, стартовую загрузку из PostgreSQL и публикацию в Kafka. Добавлены миграция, Compose-стенд и пример для ручного запуска. Контракт дополнен ответом `413` для тела больше 1 МиБ. Секреты администратора или токены пользователей для тестов не нужны, запросы используют синтетические метки браузера.

На локальном стенде с PostgreSQL 17 и Kafka 4.1.2 прошли unit-тесты и обе интеграционные проверки с детектором гонок. В проверке записи два последовательных POST с одним токеном получили `202`. Дополнительно проверены обычный запуск через `cmd/televote`, чтение демо-записи консольным потребителем и ответ `503` примерно через пять секунд при остановленном брокере. ## Решение о закрытии при нескольких репликах

Это позволяет закрыть эфир при падении писателя и допускает пропуск заявки, записанной после маркера. Решение относится к дизайну многорепличной версии. ## Закрытие по подтверждениям реплик с резервным тайм-аутом

> давай тогда реализуем это с drained и потом с 5 сек таймаутом

Уточнили предыдущее решение. Каждая реплика регистрируется перед приёмом голосов и записывает `drained_at`, когда закончились её HTTP-обработчики и отправки в Kafka. Как только подтвердили все, можно ставить маркеры. Если реплика упала или зависла, с `closes_at + 5 секунд` оставшиеся могут продолжить подсчёт. PostgreSQL хранит одно решение для каждой версии опроса. [Координация реплик](internal/repository/closurerepo/postgres.go) · [Обработчик дедлайна](internal/app/counting.go)

Codex реализовал регистрацию, миграцию, закрытие и тесты. В интеграционном прогоне на Kafka и PostgreSQL зритель выбрал A, затем через вторую реплику выбрал B. При обычном закрытии учтён B. При задержке записи B до момента после первого маркера учтён A. Тест проверяет позицию записи в Kafka, причину закрытия и итог в PostgreSQL. [Интеграционный сценарий](tests/integration/count_replicas_test.go)

После изменения повторили минутный нагрузочный сценарий. Все 30 000 POST получили `202`, а в PostgreSQL сохранились 27 273 бюллетеня. На пиковой фазе один локальный HTTP-обработчик подтвердил 999,9 POST/с. Финал сохранился через 50,9 мс после дедлайна. [Условия замера](README.md#тесты)
