# Как принять 100 млн голосов за минуту

**Для национального эфира выбираем Go API, реплицированный журнал Kafka и пакетный подсчёт по партициям. PostgreSQL хранит опросы и обезличенные итоги.** Зрителю важно успеть отправить ответ за минуту. Редакции нужен точный итог. Для проекта принимаем отдельную цель — опубликовать его в течение пяти минут после закрытия. Это позволяет во время эфира потратить ресурсы прежде всего на надёжный приём. [Azure Architecture Center о сглаживании нагрузки очередью](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)

## Сколько записей пройдёт через систему

Считаем всех 100 млн зрителей. В среднем это 1,67 млн новых бюллетеней в секунду, а при двукратном пике — 3,33 млн. Если 10% зрителей отправят ответ ещё раз и повторы распределятся как первые запросы, Kafka должна выдержать **3,67 млн записей/с в пике**. Обработчикам предстоит прочитать 110 млн записей. Полный проход за следующие 300 секунд требует в среднем **367 тыс. записей/с**. На запуск, публикацию и восстановление после сбоя нужен запас. Число брокеров и партиций определит стенд с включённой репликацией, одновременными GET формы и отказом узла. [Google SRE о подготовке к пиковому трафику](https://sre.google/sre-book/reliable-product-launches/)

## Почему выбираем пакетный подсчёт

При прямой записи в шардированный PostgreSQL уникальный ключ «опрос, зритель» позволяет сразу подтвердить учтённый выбор. Для этого SQL-шарды должны во время эфира обслуживать весь поток попыток, проверять уникальность и сохранять 100 млн новых строк. При обработке каждого события через Redis пришлось бы хранить отметки зрителей и обновлять промежуточные счётчики. Для итогового отчёта достаточно один раз собрать суммы по завершённым партициям. [Уникальные ограничения и INSERT в PostgreSQL](https://www.postgresql.org/docs/18/sql-insert.html)

Sky Italia тоже отделила сервис голосования от обработки событий. Для сезона X Factor 2022 компания указывает пик 400 тыс. голосов **за минуту**. Достигнутая скорость относится к их эфиру. Для нас важнее продуктовое решение команды — ускорить агрегацию, когда ведущему понадобился промежуточный рейтинг. В нашем ТЗ такого требования нет. [Кейс Sky Italia и AWS](https://aws.amazon.com/blogs/media/sky-italia-improves-performance-lowers-costs-84-percent-by-insourcing-its-voting-platform-for-live-tv-productions-with-aws/)

## Что происходит с голосом

Прямой GET отдаёт форму из памяти Go API. На POST сервис проверяет выбор и направляет все попытки одного браузера в одну партицию по псевдониму, действующему для этого опроса. После подтверждения реплик API отвечает `202` — «получено для обработки». При потере ответа зритель может повторить тот же выбор с прежним токеном. [RFC 9110 о статусе 202](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) · [Apache Kafka о партициях и порядке записей](https://kafka.apache.org/41/getting-started/introduction/)

API фиксирует время получения полного POST и передаёт его в Kafka. После дедлайна экземпляры API завершают уже начатые публикации, затем координатор записывает маркер закрытия в каждую партицию. Обработчик читает до маркера и проверяет окно по серверному времени приёма и для каждого ключа учитывает последний допустимый бюллетень по порядку записи в партиции. Заявка, принятая API в пределах минуты, может получить подтверждение Kafka после её окончания. В PostgreSQL обработчик сохраняет абсолютные суммы и границы прочитанного диапазона. После сбоя можно перечитать незавершённую партицию, пока её записи доступны. Админка показывает окончательный итог после фиксации результатов всех партиций, включая пустые.
