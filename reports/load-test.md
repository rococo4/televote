## Как воспроизвести

Из корня репозитория запустите зависимости и тест. Он сам создаст опрос, топик и HTTP-сервер. Нагрузочный прогон лучше запускать отдельно от других тестов.

```sh
docker compose -f test-env/compose.yaml up -d --wait
go test -tags=integration,load -run '^TestSubmitVoteLoad$' -count=1 -v -timeout=3m ./tests/integration
```

Для другого стенда задайте `DATABASE_URL` и `KAFKA_BROKERS`. Тесту нужны права создавать схемы PostgreSQL и топики Kafka. [Настройки](../README.md#локальный-запуск) · [Код теста](../tests/integration/submit_vote_load_test.go)

## Что измеряем

- Генератор заранее готовит cookie для 27 273 зрителей. Каждый десятый повторяет голос с той же cookie. За минуту запланированы 30 000 POST, в среднем 500/с. Половина приходится на первые 15 с (1 000/с), вторая половина — на следующие 45 с (333⅓/с). Получение cookie через GET проверяет [отдельный e2e-тест](../tests/e2e/poll_lifecycle_test.go).
- Одновременно выполняются до 128 запросов. Если все слоты заняты, генератор пропускает отправку (`dropped`). После паузы планировщика он продолжает с прежним интервалом, поэтому фаза может растянуться. Скорость в таблицах — число `202` с ожидаемым телом за фактическое время фазы. Задержки измеряются до чтения ответа и включают отправленные запросы с HTTP 500.
- Опрос закрывается через 70 с. Тест раз в 20 мс проверяет итог в PostgreSQL. Для `PASS` нужны 30 000 ответов `202`, 27 273 бюллетеня, из них 13 637 за A и 13 636 за B. Независимый читатель сверяет записи Kafka с отправками по каждому ключу и читает маркеры закрытия.

### Почему задержались первые голоса

В диагностическом прогоне через 14 мс после первой отправки Kafka вернула `NOT_LEADER_FOR_PARTITION`. Для одной из партиций нового топика клиент повторно запросил сведения о лидере только через 5 с. К тому времени у голоса истёк срок отправки. Пока HTTP-запросы ждали Kafka, они занимали слоты генератора. [Трасса и команды воспроизведения](load-diagnostic.txt)

Снизили `MetadataMinAge` с 5 с до 50 мс. При ошибке клиент может раньше узнать нового лидера. При массовой смене лидеров это увеличит число запросов метаданных. На коммите `0748ae1` повторили исходный профиль без диагностического логирования. [Изменение](https://github.com/rococo4/televote/commit/0748ae184502d49ffa78e32f6c62163c930c2033) · [Настройка клиента](../internal/adapter/kafka/producer.go)

## Стенд и границы замера

Apple M2 Pro, 12 ядер, 32 ГиБ, macOS 27.0.1 arm64, Go 1.26.0. Генератор и один HTTP-сервер работали в одном процессе по loopback. На машине нативно запущены PostgreSQL 17.12 и один брокер Kafka 4.1.2 (KRaft). У топика четыре партиции, `replication.factor=1`, `min.insync.replicas=1`. На стенде `group.initial.rebalance.delay.ms=0`. В Compose действует стандартная задержка Kafka, которая может повлиять на время до итога.

Для проверки проектного пика 3,67 млн POST/с потребуются отдельные генераторы и кластер с межузловой репликацией. В такой тест также должны войти GET всех зрителей, TLS и балансировщик. [Расчёт нагрузки](../DESIGN.md)
