## Замечания по коду и дизайну

1. Несколько API-реплик могут одновременно перечитать одни и те же партиции. Уникальные ключи в PostgreSQL защищают суммы от удвоения, но чтение, CPU и память дублируются. Каждой партиции нужен один обработчик с передачей работы после сбоя. [Запуск на реплике](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/app/publication.go#L83) · [Обход партиций](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/service/counting/count.go#L87)
2. Дизайн предполагает хранение 24 часа и `retention.bytes=-1`. API задаёт только `cleanup.policy=delete`. При малом лимите брокер может удалить начало журнала, и отчёт останется в `finalizing`. Стоит проверять фактические лимиты хранения. Устойчивость к отказу зоны также зависит от RF, `min.insync.replicas` и размещения брокеров. [Настройки топика](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/adapter/kafka/topics.go#L27) · [Политика хранения](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/DESIGN.md#L101)
3. При старте ошибка подготовки одного топика останавливает HTTP-сервис и планировщик этой реплики. Регистрацию проблемного опроса можно повторить отдельно. [Запуск](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/app/app.go#L82)
4. Загрузка правил на холодной реплике использует контекст первого обращения. Если зритель отменит запрос, загрузка прервётся для всех ожидающих. Ей нужен собственный тайм-аут, а каждому запросу — возможность прекратить ожидание. [Загрузка правил](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/app/publication.go#L16)
5. После успешной публикации сбой локальной регистрации даёт `503`. Если API назначил UUID сам, администратор его не узнает и повтором создаст ещё один опрос. Нужно вернуть сохранённый ID. С клиентским UUID повтор уже безопасен. [Сценарий создания](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/service/polls/service.go#L56)
6. Обработчики ждут маркеры во всех партициях. Пока у одной партиции нет лидера, остальные тоже ждут и теряют время до удаления сегментов. Каждую можно считать после её собственного маркера и публиковать общий итог по готовности всех. [Цикл закрытия](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/service/counting/count.go#L78)

## Замечания к сдаче и замерам

- На одном процессе с RF=1 измерено около 1 000 POST/с. Для 100 млн зрителей, 10% повторов и пика ×2 расчёт даёт 3,67 млн POST/с. Тест мог пройти при растянувшейся пиковой фазе. Нужен допуск на фактическую частоту подачи запросов и отдельный кластерный прогон. [Проверка фазы](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/tests/integration/submit_vote_load_test.go#L224) · [Условия замера](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/README.md#тесты)
- Для расчёта использовали 128 байт на событие. В той версии при выборе `[1]` и UTC-метке с девятью знаками после секунды JSON занимает 123 байта плюс 32 байта ключа. Это около 568 МБ/с на пике и 17,05 ГБ за эфир до сжатия, служебных полей и репликации. Стоит замерить размеры реальных бюллетеней. [Формат](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/adapter/kafka/producer.go#L73) · [Расчёт](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/DESIGN.md#L105)
- Повтор `seed-demo.sh` повышает версию и использует прежний топик. Если Kafka уже удалила первые сегменты, новая версия примет голоса и не сможет пересчитать их с offset 0. Для нового эфира нужен отдельный топик. [Демо-скрипт](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/test-env/seed-demo.sh#L15)
- Команда интеграционных тестов в README пропускала проверку повторного использования совместимого Kafka-топика. [README](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/README.md#L109) · [Тест адаптера](https://github.com/rococo4/televote/blob/d65e27e7f9b4331c4194ba43e55572f8482d332c/internal/adapter/kafka/topics_integration_test.go#L19)

## Воспроизведение

На коммите `d65e27e` запустите зависимости из Compose и выполните штатные тесты из корня репозитория.

```sh
go test -race -count=1 -tags=integration,e2e -timeout=2m ./...
```

В отдельной рабочей копии того же коммита примените [патч к четырём тестам](review-d65e27e.patch) и запустите их.

```sh
git apply --unidiff-zero /путь/к/review-d65e27e.patch
go test -race -tags=integration -count=1 -run '^TestReview' -v ./internal/api/http/votes ./internal/repository/resultsrepo ./tests/integration
```

`PASS` этих четырёх тестов означает, что описанное поведение воспроизвелось. После исправления нужно поменять ожидания. Минутный нагрузочный тест в рамках ревью не повторяли.
