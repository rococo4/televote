# Ревью Televote перед сдачей

Это архив ревью коммита `d65e27e`. Указанные далее состояние публичной ветки, результаты тестов и замечания относятся к тому снимку. Текущая версия и результаты повторной проверки описаны в [README](../README.md) и [протоколе нагрузки](load-test.md).

Проверяемая версия — `d65e27e`. Все три операции из ТЗ работают в локальном стенде. На момент ревью публичная ветка `rococo4/televote:main` указывала на `43e55ea`. Между ней и проверенной реализацией десять коммитов. В опубликованном дереве есть дизайн и исследовательские материалы. Go-сервис, Compose и тесты пока доступны локально.

Первыми стоит исправить повторную привязку непустого журнала и потерю признака конфликта при подсчёте. В обоих случаях редактор может получить правдоподобный `final` и по ответу API не узнать о проблеме.

## Замечания по коду и дизайну

1. **Масштабирование подсчёта.** Каждая API-реплика запускает задачу на тот же опрос, один раз читает список незавершённых партиций и идёт по нему с начала. При одновременном старте несколько реплик могут воспроизвести один и тот же журнал целиком. Уникальные ключи в PostgreSQL защищают суммы, но Kafka, CPU и память тратятся повторно. Для целевого масштаба нужна выдача партиции одному исполнителю с возможностью перехвата после его сбоя. [Запуск на реплике](../internal/app/publication.go#L83) · [Обход партиций](../internal/service/counting/count.go#L87)
2. **Сохранность входных данных.** Дизайн предусматривает 24 часа хранения и `retention.bytes=-1`. API задаёт топику только `cleanup.policy=delete`. При унаследованном малом лимите брокер может удалить начало журнала до подсчёта. Сервис обнаружит потерю, отчёт останется в `finalizing`. Следует задавать или проверять фактические параметры хранения для окна эфира и восстановления. Заявленная устойчивость к отказу зоны также зависит от RF, `min.insync.replicas` и размещения брокеров. [Настройки топика](../internal/adapter/kafka/topics.go#L27) · [Политика хранения](../DESIGN.md#L101)
3. **Изоляция сбоев.** При рестарте ошибка подготовки топика одного открытого опроса прерывает запуск всего HTTP-сервиса и планировщика. Исправные опросы этой реплики также становятся недоступны. Ошибку отдельного опроса стоит изолировать и повторять его регистрацию через существующий механизм обнаружения. [Запуск](../internal/app/app.go#L82)
4. **Холодный кэш.** Общая загрузка правил использует контекст первого HTTP-запроса. Его отмена прерывает загрузку для остальных зрителей, ожидающих тот же опрос. Общей операции нужен серверный контекст с тайм-аутом и отдельная отмена ожидания для каждого клиента. [Загрузка правил](../internal/app/publication.go#L16)
5. **Ошибка создания без клиентского UUID.** Публикация в PostgreSQL может завершиться успешно, а локальная регистрация — с ошибкой. Редактор получит `503` без назначенного UUID, фоновое обнаружение сможет активировать опрос, повтор без ID создаст ещё один. Клиентский UUID уже позволяет безопасно повторить запрос. Для режима с серверным UUID стоит возвращать известный ID при ошибке после резервирования. [Сценарий создания](../internal/service/polls/service.go#L56)
6. **Сбой одной партиции задерживает контрольные точки остальных.** Чтение начинается только после подтверждения маркеров во всех партициях. Пока у одной нет лидера, исправные также не сохраняют свои суммы. Если восстановление затянется, останется меньше времени до удаления их входных данных. Можно обрабатывать каждую партицию по готовности её маркера, а общий итог по-прежнему публиковать только после всех частичных. [Цикл закрытия](../internal/service/counting/count.go#L78)

## Замечания к сдаче и замерам

- Локальный замер из README подтверждает около 1 000 POST/с для одного процесса и RF=1. Цель 3,67 млн POST/с включает все 100 млн зрителей, пик ×2 и 10% повторов. Кластерный замер этой цели остаётся открытым. Нагрузочный тест проверяет число успешных ответов и итог, но может пройти при растянувшейся пиковой фазе. Для проверки пропускной способности нужен допуск на фактически поданную скорость в каждой фазе. [Проверка фазы](../tests/integration/submit_vote_load_test.go#L224) · [Условия замера](../README.md#тесты)
- Оценка полосы использует условные 128 байт на событие. Для версии 1, выбора `[1]` и UTC-метки с девятью десятичными знаками JSON занимает 123 байта, ключ — ещё 32. При таком примере получается примерно 568 МБ/с в пике и 17,05 ГБ за эфир до сжатия, служебных данных и репликации. Для планирования стоит измерить распределение размеров на типичных бюллетенях. [Формат](../internal/adapter/kafka/producer.go#L73) · [Расчёт](../DESIGN.md#L107)
- Повтор `seed-demo.sh` повышает версию опроса и переиспользует топик. После удаления старых сегментов следующая версия сможет принять голоса, но чтение с offset 0 завершится ошибкой. Для долговременного демостенда нужен отдельный топик на версию. [Демо-скрипт](../test-env/seed-demo.sh#L15)
- Команда интеграционных тестов в README пропускает тест Kafka-адаптера на повторное использование совместимого топика. Проверенный полный вариант приведён ниже. [README](../README.md#L109) · [Тест адаптера](../internal/adapter/kafka/topics_integration_test.go#L19)

## Воспроизведение

На запущенном Compose-стенде из корня проекта полный штатный прогон выполняется командой

```sh
go test -race -count=1 -tags=integration,e2e -timeout=2m ./...
```

Для повторения четырёх наблюдений приложен [патч диагностических тестов](review-d65e27e.patch). В отдельной рабочей копии коммита `d65e27e` примените его через `git apply --unidiff-zero /путь/к/review-d65e27e.patch`, затем выполните

```sh
go test -race -tags=integration -count=1 -run '^TestReview' -v ./internal/api/http/votes ./internal/repository/resultsrepo ./tests/integration
```

Эти четыре диагностических теста проходят, когда воспроизводится описанное поведение. При исправлениях их ожидания нужно заменить целевыми. Минутный нагрузочный прогон в рамках ревью повторно не запускался.
