# Пакеты Televote на примере приёма и подсчёта голосов

Первый сценарий — принять анонимный бюллетень в опубликованном опросе и подтвердить запись в Kafka. В предметной модели `Poll` задаёт окно голосования и правила выбора, `Choice` обозначает вариант, а `Ballot` содержит выбранные ID. В Kafka попадает событие `VoteSubmitted` с ID и версией опроса, временем приёма, ключом зрителя и вариантами. Токен браузера нужен API для расчёта ключа. [HTTP-контракт](../api/openapi.yaml) · [Правила голосования и подсчёта](../DESIGN.md)

Контракт ведём вручную в OpenAPI YAML. Входной JSON обрабатывает пакет `votes`. `cmd/televote/main.go` вызывает `app.Run`. При запуске `app` открывает пул PostgreSQL, создаёт Kafka producer и собирает обработчик через `app.NewHandler`. Тот загружает опубликованные опросы через `pollsrepo.LoadPublished`, проверяет доступность брокера и регистрирует UUID экземпляра в `closurerepo` для версий, по которым тот сможет принимать голоса. Зарегистрированные правила используются в памяти при обработке POST. Пакет `votes` регистрирует маршрут в `http.ServeMux`.

## Что происходит при POST

Допустим, в A/B-опросе вариант B имеет ID 2. Браузер отправляет следующий запрос.

```http
POST /api/polls/c17c57c4-51b1-4d95-841f-1e44356f5608/votes
Content-Type: application/json

{"token":"7ae145ffec3648e0b8c637d601cc4682","choices":[2]}
```

1. **HTTP.** Обработчик читает полное тело и вызывает `voting.Begin(pollID)`. Сервис находит опрос в памяти, один раз фиксирует серверное время и под той же локальной блокировкой проверяет окно и регистрирует начатый запрос. Так отправка в Kafka может завершиться после дедлайна. Затем обработчик разбирает JSON и декодирует 32 hex-символа токена в 16 байт. При ошибке завершает регистрацию и возвращает соответствующий HTTP-статус.
2. **Сценарий и доменные правила.** Обработчик передаёт зарегистрированный запрос, токен и выбор в `voting.Submit`. Сервис вызывает `poll.ValidateBallot`. Для нашего примера вариант 2 должен принадлежать опросу, а число выбранных вариантов — быть равно одному. Для множественного выбора тот же метод проверяет минимум, максимум и уникальность ID.
3. **Запись.** Сервис вычисляет `SHA-256(poll_uuid_bytes || token_bytes)`, собирает `VoteSubmitted` и вызывает `Publisher.Publish`. Реализация в `adapter/kafka` выбирает партицию по ключу, используя число партиций данного эфира, и дожидается подтверждения Kafka. Начатая публикация учитывается до завершения работы producer, в том числе при отключении клиента. Сервер ограничивает ожидание своим тайм-аутом.
4. **Ответ.** После подтверждения HTTP-обработчик отвечает `202 {"status":"accepted"}`. При недоступности Kafka или тайм-ауте возвращает `503`. Повтор с тем же токеном может ещё раз получить `202`. После закрытия обработчик подсчёта учтёт последний допустимый бюллетень по этому ключу до первого маркера в партиции. Маршрут голосования работает без запросов к PostgreSQL.

## Что происходит после закрытия

1. `app` ставит локальный таймер на дедлайн каждого загруженного опроса. В момент закрытия каждая реплика завершает приём новых заявок и через `closurerepo` ставит `drained_at`, когда закончились уже принятые запросы и вызовы Kafka producer.
2. `closurerepo` разрешает закрытие сразу, если все зарегистрированные писатели отметились в срок. Первая реплика, которая создаёт строку версии в `poll_closures`, задаёт общую границу ожидания по `POLL_CLOSE_GRACE_PERIOD`. Если список пуст или хотя бы одна реплика не отметилась к этой границе, доступно решение `timeout`. Решение сохраняется один раз. Любой работающий экземпляр может продолжить с него после сбоя.
3. Kafka-адаптер пишет `CLOSE` с явным номером партиции. `service/counting` читает до первого маркера своей версии и запоминает последний допустимый набор вариантов каждого ключа. Одновременно читаются до четырёх партиций на процесс. В `resultsrepo` уходят диапазон, число бюллетеней и суммы по каждому варианту. После фиксации всех партиций SQL публикует одну строку в `poll_results`. [Локальный запуск и команды SQL](../README.md#подсчёт-и-просмотр-результата)

## Интеграционные и e2e-тесты

Интеграционные тесты написаны на Go. Один Compose-стенд поднимает PostgreSQL и Kafka. При первом запуске на новом томе PostgreSQL применяет все миграции. Для независимых прогонов используем отдельные опросы и топики.

**Интеграционные тесты первого POST.** В `postgres_integration_test.go` заполняем таблицы и проверяем, что `LoadPublished` возвращает опубликованные правила с правильными вариантами и границами окна. В `tests/integration/submit_vote_test.go` создаём открытый опрос и топик до запуска HTTP-обработчика. Собираем его с настоящими репозиторием и Kafka producer и обслуживаем через `httptest.NewServer`. Отправляем два POST с одним токеном и разным выбором, второй после подтверждения первого. Оба должны вернуть `202`. Отдельным Kafka consumer читаем события и сверяем полный ключ зрителя, номер партиции, порядок вариантов и серверную метку приёма. Так выявляется случай, когда HTTP вернул ожидаемый статус, но событие опубликовано с неверным ключом или содержимым.

В отдельном интеграционном прогоне останавливаем локальный брокер после готовности приложения. POST должен завершиться с `503` в пределах тайм-аута публикации. При тайм-ауте запись могла состояться, поэтому проверяем HTTP-ответ без предположений о количестве событий в журнале.

**Интеграционный тест подсчёта.** В `count_votes_test.go` отправляем `X → A`, `X → B`, `Y → B` в две из четырёх партиций. После дедлайна воспроизводим состояние частично завершённого подсчёта и проверяем, что в PostgreSQL пока нет финала. Затем обработчик заканчивает подсчёт. В базе должны появиться итоги всех четырёх партиций и один финал с двумя бюллетенями, A = 0, B = 2. Повторная проверка через новый экземпляр сверяет те же числа.

**Запланированный e2e всего опроса.** После реализации админки добавим `tests/e2e/poll_lifecycle_test.go`. Он будет создавать и проверять данные через те же HTTP-ручки, что редактор и зрители.

1. С административным секретом создать A/B-опрос через `POST /admin/polls` и дождаться открытия по `GET /admin/polls/{id}/results`.
2. По очереди отправить `X → A`, `X → B`, `Y → B` через публичный POST. X и Y — два разных токена. Проверить каждый ответ `202` до следующей отправки.
3. Опросить ручку результатов до `final` с ограничением времени. Ожидать ровно два бюллетеня, ноль голосов за A и два за B. Это проверяет, что второй выбор X заменил первый. После закрытия свежая попытка получает `410`.

Пограничные 59,9 и 60,1 секунды проверяем в `submit_test.go` с управляемыми часами и задержкой отправителя. Это позволяет воспроизвести гонку на дедлайне независимо от скорости тестового стенда.

Для интеграционных тестов нужен тег Go `integration` и запущенный Compose-стенд.

```sh
go test ./...
go test -race -count=1 -tags=integration ./internal/repository/... ./tests/integration
```

## Куда добавлять изменения

| Изменение | Место и проверка |
|---|---|
| Новый HTTP-метод, например создание опроса редактором | Добавить операцию в `api/openapi.yaml`, обработчик в `internal/api/http/adminpolls/`, сценарий создания в `internal/service/polls/`. Формат запроса, авторизацию и статусы проверить через `httptest`. Эти пакеты появятся вместе с методом. |
| Новое правило бюллетеня | Расширить `entity.Poll.ValidateBallot` и добавить пример в `entity/poll_test.go`. Например, при разрешённых двух ответах `[1,2]` допустим, а `[1,1]` даёт ошибку. |
| Ещё один запрос к таблицам опросов | Добавить SQL в `repository/pollsrepo/queries/`, метод в `postgres.go` и интеграционный тест в `postgres_integration_test.go`. Изменение таблиц получает следующую нумерованную миграцию. |
| Изменение обработки тайм-аута или дедлайна | Проверить в `service/voting/submit_test.go` с управляемыми часами и тестовой реализацией `Publisher`. Принятый на 59,9-й секунде бюллетень может получить подтверждение на 60,1-й. Новый запрос в этот же момент получает `410`. |

Пакет выбирается по роли зависимости. Клиент внешнего сервиса, например Kafka, живёт в `adapter/<имя>`. SQL и преобразование строк в доменные типы принадлежат репозиторию. Версию сторонней библиотеки фиксируем в `go.mod`, а импорт размещаем в пакете, который её использует. Например, драйвер PostgreSQL нужен `app` для создания пула и `pollsrepo` для запросов, а Kafka-клиент нужен адаптеру. Интерфейс из одного метода `Publish` объявляет его потребитель `service/voting`. Это позволяет проверить сценарий обычным Go-тестом с подставным отправителем.
