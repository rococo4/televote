# Пакеты Televote на примере приёма и подсчёта голосов

Первый сценарий — принять анонимный бюллетень в опубликованном опросе и подтвердить запись в Kafka. В предметной модели `Poll` задаёт окно голосования и правила выбора, `PollChoice` обозначает вариант, а `Ballot` содержит выбранные ID. В Kafka попадает событие `VoteSubmitted` с ID опроса, временем приёма, ключом зрителя и вариантами. API вычисляет ключ по ID опроса и анонимной cookie, которую сервер выдаёт браузеру вместе с вопросом. [HTTP-контракт](../api/openapi.yaml) · [Правила голосования и подсчёта](../DESIGN.md)

Контракт ведём вручную в OpenAPI YAML. Входной JSON обрабатывает пакет `votes`. `cmd/televote/main.go` вызывает `app.Run`. При запуске `app` открывает пул PostgreSQL, создаёт Kafka producer и вызывает `app.New` для сборки приложения. Конструктор загружает опубликованные опросы через `pollsrepo.LoadPublished`, проверяет доступность брокера и регистрирует UUID экземпляра в `closurerepo` для опросов, по которым тот сможет принимать голоса. Зарегистрированные правила используются в памяти при обработке POST. Пакет `votes` регистрирует маршрут в `http.ServeMux`.

## Что происходит при POST

Зритель открыл вопрос через `GET /api/polls/{id}` и выбрал вариант B с ID 2. Браузер сам прикладывает сохранённую cookie к запросу.

```http
POST /api/polls/c17c57c4-51b1-4d95-841f-1e44356f5608/votes
Content-Type: application/json
Cookie: televote_voter=7ae145ffec3648e0b8c637d601cc4682

{"choices":[2]}
```

1. **HTTP.** Обработчик читает полное тело и вызывает `voting.Begin(pollID)`. Сервис находит опрос в памяти, один раз фиксирует серверное время и под той же локальной блокировкой проверяет окно и регистрирует начатый запрос. Так отправка в Kafka может завершиться после дедлайна. Затем обработчик читает 16-байтовый идентификатор зрителя из cookie и разбирает JSON. При ошибке завершает регистрацию и возвращает соответствующий HTTP-статус.
2. **Сценарий и доменные правила.** Обработчик передаёт зарегистрированный запрос, идентификатор из cookie и выбор в `voting.Submit`. Сервис вызывает `poll.ValidateBallot`. Для нашего примера вариант 2 должен принадлежать опросу, а число выбранных вариантов — быть равно одному. Для множественного выбора тот же метод проверяет минимум, максимум и уникальность ID.
3. **Запись.** Сервис вычисляет `SHA-256(poll_uuid_bytes || token_bytes)`, собирает `VoteSubmitted` и вызывает `Publisher.Publish`. Реализация в `adapter/kafka` выбирает партицию по ключу, используя число партиций данного эфира, и дожидается подтверждения Kafka. Начатая публикация учитывается до завершения работы producer, в том числе при отключении клиента. Сервер ограничивает ожидание своим тайм-аутом.
4. **Ответ.** После подтверждения HTTP-обработчик отвечает `202 {"status":"accepted"}`. При недоступности Kafka или тайм-ауте возвращает `500`. Повтор с той же cookie может ещё раз получить `202`. После закрытия обработчик подсчёта учтёт последний допустимый бюллетень по этому ключу до первого маркера в партиции. Для известного опроса запрос целиком обрабатывается по правилам из памяти. При промахе реплика сначала загружает опубликованный опрос из PostgreSQL. Если до закрытия осталось время, она регистрируется как писатель и повторяет допуск. Серверное время фиксируется при успешном допуске.

## Что происходит после закрытия

1. При публикации или обнаружении опроса `app` запускает `finishPoll` с таймером на `closes_at`. Другие реплики узнают об опросе при первом GET/POST или при загрузке незавершённых опросов раз в пять секунд. В момент закрытия каждая реплика завершает приём новых заявок и через `closurerepo` ставит `drained_at`, когда закончились уже принятые запросы и вызовы Kafka producer.
2. После ожидания собственных отправок `app` вызывает `closurerepo.Decide`. Последний писатель может сразу начать закрытие. Если другой писатель ещё не отметился, репозиторий возвращает сохранённый для опроса срок `closes_at + grace`. Реплика один раз ждёт до него по отменяемому таймеру и снова вызывает `Decide`. Если в срок отметились все писатели, будет принято решение `drained`. Если к окончанию ожидания список пуст или кто-то не успел, доступно решение `timeout`. Любой работающий экземпляр может продолжить с уже сохранённого решения после сбоя.
3. Kafka-адаптер отправляет `CLOSE` в партиции, для которых PostgreSQL ещё не хранит результата. При одновременном закрытии или повторе после сбоя возможны несколько маркеров в одной партиции. Подсчёт останавливается на первом маркере. Реплики подписываются на топик с одним `group.id` для опроса. Kafka назначает участникам партиции и перераспределяет их при уходе участника. Внутри каждой назначенной партиции `service/counting` учитывает последний допустимый набор вариантов зрителя до первого маркера.
4. На маркере `resultsrepo` сохраняет позицию первого `CLOSE`, число бюллетеней и суммы по каждому варианту. После этого адаптер подтверждает следующую позицию этой партиции в Kafka. Новый владелец перечитает незавершённую партицию с начала. Когда готовы все частичные итоги, SQL публикует одну строку в `poll_results`. [Команда записи частичного итога](../internal/repository/resultsrepo/queries/save_partition.sql) · [Суммирование в SQL](../internal/repository/resultsrepo/queries/finalize.sql)

При принудительном закрытии зависшая реплика всё ещё может получить ACK за ранее начатый POST. Если запись оказалась после первого `CLOSE` своей партиции, она останется в Kafka и не войдёт в отчёт.

## Интеграционные и e2e-тесты

Интеграционные тесты написаны на Go. Один Compose-стенд поднимает PostgreSQL и Kafka. При первом запуске на новом томе PostgreSQL применяет все миграции. Для независимых прогонов используем отдельные опросы и топики.

**Интеграционные тесты первого POST.** В `postgres_integration_test.go` заполняем таблицы и проверяем, что `LoadPublished` возвращает опубликованные правила с правильными вариантами и границами окна. В `tests/integration/submit_vote_test.go` создаём открытый опрос и топик до запуска HTTP-обработчика. Собираем его с настоящими репозиторием и Kafka producer и обслуживаем через `httptest.NewServer`. Отправляем два POST с одной cookie и разным выбором, второй после подтверждения первого. Оба должны вернуть `202`. Отдельным Kafka consumer читаем события и сверяем полный ключ зрителя, номер партиции, порядок вариантов и серверную метку приёма. Так выявляется случай, когда HTTP вернул ожидаемый статус, но событие опубликовано с неверным ключом или содержимым.

Ответ HTTP при сбое публикации проверяет `internal/api/http/votes/handler_test.go`. Тестовый отправитель возвращает ошибку, клиент получает `500`. В реальном запросе тайм-аут ожидания Kafka оставляет исход записи неизвестным.

**Интеграционный тест подсчёта.** В `count_votes_test.go` отправляем `X → A`, `X → B`, `Y → B` в две из четырёх партиций. После дедлайна воспроизводим состояние частично завершённого подсчёта и проверяем, что в PostgreSQL пока нет финала. Затем обработчик заканчивает подсчёт. В базе должны появиться итоги всех четырёх партиций и один финал с двумя бюллетенями, A = 0, B = 2. Повторная проверка через новый экземпляр сверяет те же числа.

**Сквозной тест.** В `tests/e2e/poll_lifecycle_test.go` два экземпляра приложения с отдельными HTTP-серверами, пулами PostgreSQL и клиентами Kafka работают в одном тестовом Go-процессе и используют общую чистую схему PostgreSQL. Тест создаёт опрос и проверяет отчёт через административные ручки, а голоса отправляет через публичный POST.

1. С административным секретом создать уже открытый A/B-опрос через `POST /admin/polls`.
2. X получает cookie на первой реплике, отправляет A на второй, теряет ответ `202` и повторяет A с той же cookie. Затем X меняет выбор на B. Y открывает опрос с другой cookie и тоже выбирает B.
3. Убедиться, что до закрытия отчёт имеет статус `open`, затем дождаться `final` с ограничением времени. Ожидать ровно два бюллетеня, ноль голосов за A и два за B. Это проверяет, что второй выбор X заменил первый. После закрытия свежая попытка получает `400` с сообщением «Опрос закрыт».

Пограничные 59,9 и 60,1 секунды проверяем в `submit_test.go` с управляемыми часами и задержкой отправителя. Это позволяет воспроизвести гонку на дедлайне независимо от скорости тестового стенда.

Для интеграционных тестов нужен тег Go `integration` и запущенный Compose-стенд.

```sh
go test ./...
go test -race -count=1 -tags=integration ./internal/... ./tests/integration
go test -race -count=1 -tags=e2e ./tests/e2e
```

## Куда добавлять изменения

| Изменение | Место и проверка |
|---|---|
| Новый административный HTTP-метод | Добавить операцию в `api/openapi.yaml`, обработчик в `internal/api/http/adminpolls/`, бизнес-сценарий в `internal/service/polls/`. Формат запроса, авторизацию и статусы проверить через `httptest`. |
| Новое правило бюллетеня | Расширить `entity.Poll.ValidateBallot` и добавить пример в `entity/poll_test.go`. Например, при разрешённых двух ответах `[1,2]` допустим, а `[1,1]` даёт ошибку. |
| Ещё один запрос к таблицам опросов | Добавить SQL в `repository/pollsrepo/queries/`, метод в `postgres.go` и интеграционный тест в `postgres_integration_test.go`. Изменение таблиц получает следующую нумерованную миграцию. |
| Изменение обработки тайм-аута или дедлайна | Проверить в `service/voting/submit_test.go` с управляемыми часами и тестовой реализацией `Publisher`. Принятый на 59,9-й секунде бюллетень может получить подтверждение на 60,1-й. Новый запрос в этот же момент получает `400` с сообщением «Опрос закрыт». |

Пакет выбирается по роли зависимости. Клиент внешнего сервиса, например Kafka, живёт в `adapter/<имя>`. SQL и преобразование строк в доменные типы принадлежат репозиторию. Версию сторонней библиотеки фиксируем в `go.mod`, а импорт размещаем в пакете, который её использует. Например, драйвер PostgreSQL нужен `app` для создания пула и `pollsrepo` для запросов, а Kafka-клиент нужен адаптеру. Интерфейс из одного метода `Publish` объявляет его потребитель `service/voting`. Это позволяет проверить сценарий обычным Go-тестом с подставным отправителем.
