# Пиковая запись и повторы

## Как Shopify проверяет готовность к короткому пику

### Вывод

Для сезонной распродажи команда воспроизводит поведение покупателей и добавляет короткие всплески поверх базового трафика. На репетициях проявились узкие места в очереди аналитики и пулах соединений API. [Shopify Engineering, 20 ноября 2025](https://shopify.engineering/bfcm-readiness-2025)

### Факты

- За четыре дня Black Friday – Cyber Monday 2024 Shopify сообщил о 1,17 трлн операций записи в БД по платформе. В отдельной метрике команда приводит пики HTTP-трафика: 284 млн запросов/мин на внешней границе и 80 млн/мин на серверах приложения. [Результаты 2024 года](https://shopify.engineering/bfcm-readiness-2025)
- При подготовке к сезону 2025 года генераторы из трёх регионов имитировали просмотр, корзину и оформление заказа. В испытаниях аналитики добавляли задержку БД и отказы кеша. Чтобы результаты аналитики успевали обновляться, потребовалось увеличить число партиций Kafka в ETL. Для API команда скорректировала тайм-ауты соединений, чтобы избежать исчерпания пула. [Разделы Load testing и Analytics](https://shopify.engineering/bfcm-readiness-2025)

### Применимость

- Для нашего эфира стоит прогонять горячий опрос вместе с обычными GET страницы. Поверх исходного потока добавить десятисекундную волну POST и потерянные ответы с повторной отправкой. Измерять отдельно задержку подтверждения записи и задержку публикации полного результата.

### Границы сравнения

- Из агрегированных показателей Shopify нельзя определить скорость уникальных INSERT одного шарда, число уникальных покупателей, голоса в секунду или срок подтверждения записи на реплике. Опубликованные результаты 2024 года получены на реальной распродаже. Данные о выявленных ограничениях аналитики относятся к репетициям 2025 года. [Описание экспериментов](https://shopify.engineering/bfcm-readiness-2025)

## Как избежать повторного эффекта после тайм-аута

### Вывод

Платёжный сервис Shopify использует постоянный ключ логической операции. После обрыва клиент может повторить запрос и получить уже сохранённый результат. [Shopify Money Infrastructure, 2019](https://shopify.engineering/building-resilient-graphql-apis-using-idempotency)

### Факты

- Сервис Shopify требовал ключ идемпотентности и хранил служебную запись с уникальной парой «клиент, ключ». При завершённой операции повтору возвращали прежний ответ. Для сложной многошаговой операции сохраняли этап, с которого нужно продолжить. Это отдельная публикация о платежах, без заявлений о скорости этой операции во время BFCM. [Механизм IncomingRequest](https://shopify.engineering/building-resilient-graphql-apis-using-idempotency)
- Документация AWS отдельно разбирает повторы в Kinesis. Тайм-аут отправителя может породить две записи с разными порядковыми номерами. Сбой потребителя после записи результата и до фиксации позиции заставляет перечитать пакет. В качестве средства дедупликации AWS описывает прикладной первичный ключ события. [Руководство Kinesis](https://docs.aws.amazon.com/streams/latest/dev/kinesis-record-processor-duplicates.html)

### Применимость

- Голос с потерянным ответом повторяется с тем же ключом зрителя в рамках эфира. Для PostgreSQL уникальная строка бюллетеня одновременно удостоверяет приём. Для очереди этот же ключ передаётся в событии и сохраняется в конечной БД. Разные порядковые номера событий не дают оснований засчитать два бюллетеня.

### Границы сравнения

- Платёжная идемпотентность решает повтор одного действия. Чтобы один профиль браузера мог подать только один бюллетень в эфире, ключ для проекта должен сохраняться и при повторном открытии формы, даже если зритель пытается выбрать другой вариант.

## Как распределить горячий ключ

### Вывод

В руководстве DynamoDB описан вычислимый суффикс ключа, который распределяет записи и позволяет восстановить адрес для точечного чтения. Это пример проектирования, без замеров конкретного клиентского сервиса. [Документация DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-sharding.html)

### Факты

- AWS предлагает добавлять к общему ключу даты суффикс по хешу идентификатора заказа. Для чтения одного заказа вычисляется тот же суффикс. Для получения всех заказов за дату надо обратиться ко всем корзинам и объединить результаты. [Sharding using calculated suffixes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-sharding.html)

### Применимость

- Аналог в нашем проекте — фиксированная для эфира карта и хеш ключа зрителя. Все бюллетени одного опроса распределяются между шардами даже при победе одного варианта со 100% голосов. Все повторные отправки одного ключа попадают к одному владельцу данных. Финальный отчёт собирается из полных итогов всех шардов.

### Границы сравнения

- Пример AWS раскрывает способ адресации. Из него нельзя вывести пропускную способность PostgreSQL, число физических узлов или прирост скорости от пакетной записи с межзонной репликой.
