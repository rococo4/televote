# Приём, пакетная запись и расчёт ёмкости

## Какое подтверждение позволяет сгладить всплеск

### Вывод

Для национального эфира выбираем Go API → реплицированный журнал Kafka → отложенный точный подсчёт. Обещание POST — «ответ принят к подсчёту» после подтверждения журнала. ТЗ требует голоса и итог для редакции. Немедленная персональная проверка, выиграл ли этот ответ у другого ответа того же зрителя, была дополнительным предположением.

### Первичные источники

- Microsoft рекомендует устойчивый буфер при кратковременном превышении мощности обработчика. Рекомендация включает контроль скорости обработки, устойчивость к повторной доставке и мониторинг срока хранения. При необходимости немедленного окончательного ответа применение этого подхода ограничено. [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)
- HTTP 202 означает принятие запроса к обработке. Ответу полагается описывать текущее состояние. [RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)
- При `acks=all` Kafka ждёт все текущие синхронные реплики. При RF=3 и `min.insync.replicas=2` для успешной записи нужны минимум две такие реплики. Идемпотентность producer относится к повторам публикации записи самим producer. [Kafka topic configs](https://kafka.apache.org/41/configuration/topic-configs/#topicconfigs_min.insync.replicas) · [Kafka producer configs](https://kafka.apache.org/41/configuration/producer-configs/#producerconfigs_enable.idempotence)

### Применение

Партиции и их число фиксируем до начала эфира, реплики размещаем по зонам. Ключ записи включает эфир и стабильный браузерный идентификатор в пределах этого эфира. Повторный POST может добавить ещё одну запись и пройти ту же проверку у потребителя. На уровне приложения выбранный бюллетень определяется первым допустимым событием ключа в порядке партиции.

### Ограничение

Если заказчику понадобится персональное «уже учтён этот выбор» в ответе POST, прямой условный INSERT с уникальным ключом и синхронной репликой подходит лучше. Формулировку сообщения зрителю следует зафиксировать вместе с правилом границы минуты.

## Сколько работы действительно переносим из секунды пика

### Вывод

При 110 млн попыток за минуту и пике ×2 журнал должен принять 3,67 млн событий/с. Собственный расчёт проекта для партии одного эфира даёт 366,7 тыс. событий/с при полном чтении с нуля за следующие 300 секунд. На публикацию, запуск и аварийный повтор требуется отдельный запас.

### Первичные источники

- Kafka разбивает поток на упорядоченные партиции и сохраняет его в течение заданного периода. Потребители могут повторно читать данные. [Основы Kafka](https://kafka.apache.org/41/getting-started/introduction/#intro_concepts_and_terms)
- Kafka позволяет настраивать сохранение записей по времени и размеру. Предел в байтах действует для каждой партиции. [Kafka topic configs](https://kafka.apache.org/41/configuration/topic-configs/#topicconfigs_retention.bytes)

### Применение

Ниже десятичные единицы и условные 128 байт на событие до сжатия и служебных расходов. При 3,667 млн событий/с получается **469,3 МБ/с** данных на входе в Kafka. При RF=3 это **1,408 ГБ/с** суммарно для трёх копий, из них **938,7 МБ/с** копируются на двух последователей. 110 млн событий займут **14,08 ГБ** полезных данных до репликации и **42,24 ГБ** на три копии. Чтение 110 млн записей за 300 с потребует в среднем 46,9 МБ/с полезных данных по всему кластеру. GET формы из памяти Go масштабируется отдельно, базовый дизайн обходится без CDN.

Каждый обработчик сканирует закреплённый диапазон партиции в порядке offset и сравнивает полный псевдоним зрителя с точным множеством уже виденных ключей. При аварии можно начать эту партицию с начала. Сохранение результата по ключу «опрос, партиция, границы/версия» замещением исключает повторное прибавление при перезапуске. Такая схема держит в PostgreSQL конфигурацию и частичные итоги. Для оценки памяти 100 млн псевдонимов по 32 байта — 3,2 ГБ чистых ключей по всем партициям, плюс таблицы хеширования, буферы и запас на перекос.

### Ограничение

128 байт и пять минут — проектные допущения. Измеряются фактический размер записи, сжатие, протокольный трафик, память точного множества, длительность полного и повторного прохода. Истечение retention до полного пересчёта разрушит гарантию. Отсутствие событий при опросе Kafka в данный момент само по себе не задаёт конечную границу эфира.

## Как проверять готовность к запуску

### Вывод

Плановая скорость нового эфира известна заранее. До публикации QR готовим партиции, брокеры, соединения и набор клиентских экземпляров. Подбираем мощности по измерению всего пути POST до реплицированного подтверждения при работающих GET и при отказе узла.

### Первичные источники

- Google SRE рекомендует планировать пик запуска с учётом состава трафика, отказа ресурсов и фактического нелинейного поведения при перегрузке. [Reliable Product Launches](https://sre.google/sre-book/reliable-product-launches/)
- Google SRE описывает бюджет повторов, ограничение объёма передаваемой работы и ранний отказ при перегрузке. [Handling Overload](https://sre.google/sre-book/handling-overload/)

### Применение

Ограничиваем очередь запросов, размер пакета и возраст ожидания ACK. При тайм-ауте оставляем исход неопределённым, клиент повторяет прежние ключ и выбор. Тест имитирует волну повторов с ограничением и случайной задержкой, отказ потребителя, смену лидера партиции и одновременную выдачу форм. Проверяем факт записи принятых ответов, точный итог по каждому варианту и время финала. Для фиксированного синтетического множества все 100 млн ключей и их значения сверяются потоковым проходом по журналу отдельно от агрегатора на воспроизводимом стенде.

### Ограничение

Количество узлов, партиций и размер пакета из публичного кейса не подтверждают p99 нашей конфигурации. Критерий входа — свой пиковый профиль с репликацией, запасом на отказ и требованием 100 млн корректных бюллетеней в финале.
