# Граница минутного окна

## Когда зритель получает подтверждение

### Takeaway

Клиенту можно подтвердить сохранение заявки для обработки после успешного ответа Kafka. Окончательный учёт зависит от окна и от того, какой из ответов данного браузера был записан первым. [RFC 9110, 202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

### Cited Findings

- У топика Kafka по умолчанию используется `CreateTime`. Для отсчёта окна по приёму на брокере необходимо явно настроить `message.timestamp.type=LogAppendTime`. [Настройки топика Kafka](https://kafka.apache.org/41/configuration/topic-configs/#topicconfigs_message.timestamp.type)
- В Kafka timestamp такого события назначают по локальным часам брокера при добавлении в журнал. Официальный Java-клиент получает в результате записи партицию, смещение и метку. Go-библиотека может иметь другой интерфейс получения метаданных. [KafkaProducer](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html) · [Поле Timestamp в franz-go](https://pkg.go.dev/github.com/twmb/franz-go/pkg/kgo#Record)
- При трёх репликах, `acks=all` и `min.insync.replicas=2` успешная отправка требует подтверждения всех текущих синхронных реплик, в составе которых должно остаться минимум две. Это конфигурация для расчётного контура. [Настройки Kafka](https://kafka.apache.org/41/configuration/topic-configs/#topicconfigs_min.insync.replicas)

### Inferences

На POST проверяем форму и после ACK показываем «Ответ получен для обработки». Решение о включении события может целиком принимать счётчик при чтении брокерской метки. Недоступность журнала или тайм-аут с неопределённым результатом дают временную ошибку и возможность повтора запроса с тем же токеном. Ответ о закрытии для нового POST после дедлайна сообщает о текущей попытке. Если браузер потерял подтверждение предыдущей, история этой попытки пользователю неизвестна.

### Gaps

При реализации, если обработчик POST хочет сразу отсеивать заявку по брокерскому времени из ACK, зафиксировать библиотеку и проверить этот путь интеграционным тестом. Авторитетную метку всегда может прочитать потребитель из сохранённой записи.

## Как зафиксировать точный предел подсчёта

### Takeaway

Предлагаемый протокол задаёт предел отдельно для каждой партиции эфира. Метка брокера определяет попадание в минуту, а первый действительный служебный маркер закрытия задаёт последний доступный для подсчёта префикс журнала.

### Cited Findings

- Kafka хранит события в определённом порядке в каждой партиции. При фиксированном числе партиций и единых правилах маршрутизации записи с одинаковым ключом читаются из одной партиции в порядке добавления. [Модель топиков и партиций](https://kafka.apache.org/41/getting-started/introduction/#intro_concepts_and_terms)

### Inferences

1. До эфира фиксируем партиции, версию правил опроса, полуоткрытое окно `[opens_at, closes_at)` и ключ зрителя для маршрутизации. Все продюсеры используют одинаковую функцию выбора партиции.
2. При наступлении дедлайна координатор добавляет служебное сообщение `CLOSE(poll_id, version)` явно в каждую назначенную партицию. Для каждой партиции граница — смещение **первого** подходящего маркера данного эфира, которому брокер присвоил время не ранее `closes_at`. Ранний маркер игнорируется, при необходимости координатор повторяет отправку. Только внутренний компонент генерирует тип `CLOSE`.
3. Вклад партиции рассчитывается по `VOTE` до её маркера с `opens_at ≤ broker_timestamp < closes_at`. События после маркера не входят в результат, даже если произошёл отскок часов лидера. До маркера пропускаем отдельные поздние записи, но продолжаем читать до него. Первым допустимым смещением одного токена определяется единственный учтённый выбор.
4. При рестарте координатор может повторить те же маркеры. Первый действительный маркер и выборы до него остаются прежними. Потребитель при рестарте перечитывает партицию с начала эфира и замещает её частичный итог с указанием смещения маркера. В `final` переходим только при наличии подтверждённых итогов всех партиций. Если журнал временно недоступен, состояние остаётся `finalizing`.

### Gaps

Время каждого лидера отличается от UTC на величину реального рассогласования часов. Перед эфиром требуется синхронизация часов брокеров, измерение максимального отклонения и согласование допустимой погрешности. Маркер и смещение дают воспроизводимый ответ при повторном подсчёте. Точность соответствия внешним часам телевизионного эфира зависит от инфраструктуры.

## Как проверить границу и восстановление

### Takeaway

В испытании проверяем сохранённые в журнале события и окончательный результат каждой партиции. Число полученных клиентом HTTP-ответов служит отдельной метрикой.

### Cited Findings

- Идемпотентная отправка в Kafka предотвращает дубли из-за повторных отправок самим продюсером в рамках его гарантий. Две самостоятельные HTTP-заявки требуется дедуплицировать по общему ключу зрителя при подсчёте. [Настройки идемпотентного продюсера](https://kafka.apache.org/41/configuration/producer-configs/#producerconfigs_enable.idempotence)

### Inferences

Сценарии для стенда: запись в 59,999 с и HTTP-ответ после дедлайна, подтверждение потеряно, отправка начата до дедлайна, но записана после него, записи до и после маркера при отложенной финализации, ранний маркер из-за рассогласования часов, повторный маркер после перезапуска координатора, падение счётчика после записи частичного итога. В каждом случае итог заранее определяется диапазоном, отметкой времени и ключом зрителя.

### Gaps

Исследование определяет семантику и тесты. Фактические задержки между HTTP, добавлением в журнал, репликацией и публикацией результата можно получить только на стенде выбранной топологии.
