# Дедупликация и пересчёт по журналу

Эта исследовательская заметка сохраняет первоначальный вариант с учётом первого голоса. Позже для Televote выбрали последний допустимый бюллетень зрителя по порядку записи в партиции. [Действующее правило подсчёта](../../DESIGN.md#5-асинхронный-подсчёт-статистики)

## Как получить один бюллетень на ключ

### Takeaway

Для одного эфира выбираем фиксированные топик, число партиций, алгоритм распределения и версию правил. Каждый экземпляр API пишет все попытки с одним псевдонимом зрителя в одну партицию. [Распределение и порядок в Kafka](https://kafka.apache.org/41/getting-started/introduction/)

### Cited Findings

- Kafka хранит порядок записей внутри партиции. Для одинакового ключа при одном способе маршрутизации потребитель увидит события в порядке записи. Журнал позволяет читать этот диапазон повторно. [Гарантии Kafka](https://kafka.apache.org/41/getting-started/introduction/)
- Offset обозначает позицию записи внутри партиции. У потребителя есть отдельно текущая и сохранённая позиции. Между доступными записями могут быть пропуски в нумерации. [KafkaConsumer, Offsets and Consumer Position](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

### Inferences

После фиксации границ эфира обработчик последовательно читает свой диапазон. Если запись удовлетворяет правилам допуска, а полного ключа ещё нет в точном множестве, он сохраняет ключ, увеличивает число бюллетеней на один и каждый выбранный вариант на один. Другой выбор с тем же ключом проигрывает валидной записи с меньшим offset. Это политика проекта для конкурентных попыток. Все обработчики пользуются одной версией правил. [Основание для выбора порядка](https://kafka.apache.org/41/getting-started/introduction/)

### Gaps

Сам порядок Kafka не устанавливает справедливый дедлайн для зрителя. Нужны отдельно определённые правило допуска и границы закрытого эфира. Идемпотентность Kafka producer сама по себе не связывает два отдельных HTTP-запроса браузера. [Семантика обработки сообщений](https://kafka.apache.org/41/design/design/)

## Как публиковать результат при сбоях

### Takeaway

Обработчик завершает партицию одной записью в PostgreSQL. Храним ID эфира и поколения, партицию, границы прочитанного диапазона, версию алгоритма и абсолютные суммы. Результат воспроизводим, пока весь диапазон доступен. [Apache Kafka о внешнем хранилище](https://kafka.apache.org/41/design/design/) · [PostgreSQL INSERT](https://www.postgresql.org/docs/18/sql-insert.html)

### Cited Findings

- При записи результата во внешнюю систему фиксацию позиции и результата нужно координировать. Apache Kafka допускает хранить позицию рядом с результатом. После сбоя обработка записей может повториться. [Message Delivery Semantics](https://kafka.apache.org/41/design/design/)
- Политика топика `compact` позволяет удалять прежние значения одного ключа. Для подсчёта по первому выбору важны все исходные записи. При `delete` время и объём хранения ограничивают доступный период повторного чтения. [Настройки топика](https://kafka.apache.org/41/configuration/topic-configs/)
- Уникальное ограничение и `ON CONFLICT DO NOTHING` позволяют повторить попытку вставки уже готового результата. [Документация PostgreSQL](https://www.postgresql.org/docs/18/sql-insert.html)

### Inferences

До фиксации строки работник может потерять своё множество при аварии. Следующая попытка перечитывает с начала только незавершённую партицию. После COMMIT готовая строка позволяет пропустить работу; при конфликте сверяем границы, версию и цифры. Финализатор в транзакции сверяет точный состав партиций с сохранённой картой, включая пустые, и публикует сумму для этого поколения. Отчёт нельзя получить из частичных результатов разных версий. Для этой процедуры достаточно PostgreSQL и читаемого журнала, отдельного сервера с множеством всех зрителей не требуется. [Гарантии при обработке внешнего результата](https://kafka.apache.org/41/design/design/)

### Gaps

Удаление ранней части партиции лишает возможности полного пересчёта. Управляем сроком хранения с запасом на сбой и повтор, проверяем доступность ожидаемого начала, сохраняем исходный топик до финализации и окончания установленного срока хранения. При потере данных помечаем отчёт неполным. [Ограничения retention](https://kafka.apache.org/41/configuration/topic-configs/)

## Сколько работы останется после эфира

### Takeaway

По профилю проекта 110 млн событий за 300 секунд требуют в среднем 366,7 тыс. прочитанных событий/с. При 100 млн уникальных бюллетеней выполняется около 333,3 тыс. добавлений ключа/с. PostgreSQL получает одну строку на завершённую партицию и финальный результат. [Исходная модель нагрузки проекта](<../../DESIGN.md>)

### Cited Findings

Суммы вариантов и число бюллетеней проект считает отдельно. При нескольких вариантах в одном бюллетене счётчиков увеличивается несколько, память для одного псевдонима расходуется один раз. [Правила учёта проекта](<../../DESIGN.md>)

### Inferences

При 32-байтовом ключе сами 100 млн ключей займут 3,2 ГБ на весь опрос до накладных расходов точного хеш-множества. При равномерном распределении на P партиций один обработчик партиции хранит в среднем 3,2 ГБ / P только байтов ключей. Ещё потребуются память таблицы, буферы чтения и запас на неравномерность. Проверяем горячую партицию, максимум выбранных вариантов, рестарт в конце прохода и суммарное время до `final`. [Параметры теста](<../../DESIGN.md>)

### Gaps

Число процессов и партиций определяется замером записи с репликами, чтения, памяти, времени восстановления и дисбаланса. Для локального показа достаточно одной Kafka, PostgreSQL и Go-процесса с обработчиком. Способность принять 3,67 млн POST/с такой запуск не доказывает. [Сценарий испытания](<../../DESIGN.md>)
